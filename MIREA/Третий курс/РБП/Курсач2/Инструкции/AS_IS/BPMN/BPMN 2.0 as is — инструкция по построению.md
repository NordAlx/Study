# BPMN 2.0 as is — инструкция по построению

Построить верхний уровень и четыре детализации одной рекламной кампании. Состав функций A11–A43, роли и документы соответствуют исправленным таблицам п. 2.1 и инструкции IDEF0. Работа выполняется вручную с отдельными файлами и почтой. CRM, BPMSoft, автоматический маршрут согласования и автоматический сбор показателей в as is отсутствуют.

Инструкция исправлена после изучения всех 75 карточек основного каталога [StormBPMN](https://stormbpmn.com/elements) и дополнительной карточки Manual Task. Краткий разбор каждого элемента приведён в соседнем файле «BPMN 2.0 — справочник элементов и правил.md». Смысл спорных обозначений сверяется с [OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/PDF). Рекомендации сайта по упрощению схем не считаются запретами нотации.

## Граница процесса и участники

Основной пул — «Департамент маркетинга и рекламы». В детализациях использовать дорожки с полными названиями должностей. Дорожка обозначает распределение ответственности внутри этого участника; переход в другую дорожку сохраняет обычный поток управления. Дорожки допустимы по OMG, разд. 10.8; в нашей курсовой они нужны для согласования с оргструктурой.

| Роль | Участие |
|---|---|
| Директор департамента маркетинга и рекламы | Решение о проведении, постановка задачи, согласование |
| Менеджер рекламной кампании | Сбор данных, бриф, концепция, медиаплан, передача версий, мониторинг, отчёт |
| Специалист по разработке рекламных материалов | Тексты и макеты |
| Специалист digital-коммуникаций | Цифровые размещения, email-рассылки, показатели, корректировки |
| Trade-маркетолог | Подготовка розничного направления, ответы магазинов, корректировки |
| Маркетинговый аналитик | Сводные результаты и анализ |
| Категорийный менеджер | Коммерческие данные, продажи, получение итогового отчёта; смежный пул |
| Руководитель магазина | Готовность и подтверждения размещений; смежный пул |

Смежные пулы — «Коммерческий блок — категорийный менеджер» и «Магазины — руководитель магазина». Они остаются свёрнутыми: их внутренние работы не входят в выбранную область детализации. Чёрный ящик означает, что внутренности не показаны, а не обязательное незнание поведения участника. Продажи, ценообразование, закупка размещений, обслуживание систем и физическое размещение в магазинах остаются смежными процессами.

Сотрудников одного маркетингового процесса не разносить по отдельным пулам. Excel, Word, почта, рекламный кабинет и веб-аналитика — средства работы сотрудников; отдельных участников только для обозначения этих инструментов не создавать.

## Нужные элементы и соединения

| Элемент | Как рисовать и использовать в нашей модели |
|---|---|
| Обычная Task | Прямоугольник со скруглёнными углами, без маркера типа; действие сотрудника. Подпись — глагол и объект |
| SubProcess | На верхнем уровне прямоугольник с маленьким «+» внизу; одна из четырёх составных работ |
| Простое начальное событие | Круг с тонкой линией; без входящего потока управления |
| Простое конечное событие | Круг с толстой линией; без исходящего потока управления; подпись результата |
| XOR | Ромб с X; выбирает одну ветвь по данным; при объединении альтернатив не ждёт остальных |
| AND | Ромб с +; запускает обе обязательные ветви; объединение ждёт завершения обеих |
| OR | Ромб с кружком; запускает одно или оба направления корректировки; объединение ждёт только выбранные ветви |
| Промежуточный таймер | Двойной круг с часами; ожидание даты запуска или следующей даты контроля из медиаплана |
| Data Object | Значок документа; данные конкретной кампании, доступные операции |
| Data Store | Значок хранилища; клиентская база, журнал рассылок или архив, сохраняемые между кампаниями |
| Text Annotation | Пояснение средств труда или границы операции; не заменяет задачу, проверку или маршрут |

Обычная Task выбрана намеренно: известен исполнитель, но процессный тип задания не установлен. Работа в Excel не доказывает User Task; User Task предполагает управление жизненным циклом задания программным компонентом. Ручное заполнение файлов не является Service Task или Script Task. Проверка директором не является Business Rule Task. Manual Task не используется как общий значок любого действия человека; для этой модели достаточно обычной Task.

| Связь | Начало и конец | Смысл |
|---|---|---|
| Sequence Flow | Сплошная линия с заполненной стрелкой между событиями, задачами, подпроцессами и шлюзами одного уровня одного пула | Порядок выполнения, а не перенос файла |
| Message Flow | Штриховая линия с пустым кружком у источника и открытой стрелкой; между разными пулами, их задачами или подходящими событиями | Запрос, ответ или передача документов между участниками |
| Data Association | Точечная линия со стрелкой: документ/хранилище → задача для чтения; задача → документ/хранилище для записи | Потребление или создание информации; не запускает задачу |
| Association | Точечная линия без стрелки между пояснением и задачей | Относит текст к элементу; не передаёт управление |

Для ветвей XOR/OR писать условия на выходящих Sequence Flow. У XOR условия должны исключать друг друга и покрывать сценарий; при необходимости указывать ветвь по умолчанию. Маркер условного потока в виде маленького ромба не добавлять к выходам шлюза: он применяется к условным выходам из действий. Выходы AND не снабжать условиями выбора.

Один шлюз не принимает решение за сотрудника: сначала выполняется задача проверки, затем шлюз маршрутизирует её результат. Отказ, замечания и неполные сведения — обычные бизнес-исходы; Error, Cancel и Terminate для них не нужны. Пары разделения/объединения здесь используются для ясности маршрута; стандарт не требует механически ставить парный шлюз для каждого разветвления любого процесса.

## Декомпозиция и происхождение данных

Обозначения A1–A4 и A11–A43 связывают схемы с курсовой; это наши номера, а не ICOM-коды BPMN. Детализация описывает внутренность соответствующего SubProcess. В отдельном рисунке или файле её пул и дорожки показывают тот же организационный контекст; начальное событие означает вход в подпроцесс, а не запуск новой независимой кампании.

Sequence Flow не пересекает границу подпроцесса или пула. На верхнем уровне соединяются сами SP1–SP4; внутренние задачи соединяются на дочернем уровне. Link Events между уровнями не использовать. Call Activity нужна для вызова отдельно определённой переиспользуемой работы; сам факт отдельного рисунка не превращает нашу детализацию в Call Activity.

В отличие от IDEF0, данные не обязаны располагаться с заданной стороны задачи и не делятся четырьмя портами I/C/O/M. Источник всё равно должен быть определён: ранее выполненная задача, вход родительского подпроцесса, хранилище или сообщение смежного участника. Входы дочернего уровня доступны из родительского контекста; новые локальные документы создаются конкретными задачами. Не рисовать связи, начинающиеся в пустом месте.

Для документов конкретной кампании использовать Data Object с названием и при необходимости состоянием, например «Медиаплан [согласован]». Его область доступности не означает, что реальный файл физически удаляется после завершения процесса. Для сохранения файлов между кампаниями использовать Data Store «Архив документов кампаний».

Постоянные хранилища:

- «Клиентские контакты (файл Excel)» → T31d: чтение базы; T31d создаёт отдельный объект «Список адресатов рассылки».
- «Журнал email-рассылок (файл Excel)»: T32d записывает отправки; T33dataD читает историю и отклики.
- «Архив документов кампаний»: сохраняет файлы Word/Excel и версии материалов; задачи сохраняют свои результаты и читают существующие версии при повторном входе.
- «Архив корпоративной переписки»: хранит запросы, ответы и решения, получаемые и отправляемые через почтовый клиент.

Эти хранилища обозначают существующие раздельные файлы и переписку, а не новую единую систему. Брендбук, лимит, условия акции, шаблоны, требования каналов и правила оценки доступны до начала кампании. Подписать их источники в описании родительского процесса или объекта; не приписывать их создание задачам кампании.

Средства указывать в пояснениях к задачам раздельно: персональный компьютер; Excel; Word; почтовый клиент; корпоративная почта; графический редактор; рекламный кабинет; сервис веб-аналитики. Название программы не является самостоятельным документом данных. Используемые в расчёте затрат примеры — GIMP и Яндекс.Метрика — сохраняются.

## Диаграмма 1 — верхний уровень

Основной пул можно показать без дорожек; исполнители раскрываются ниже. Четыре свёрнутых подпроцесса: SP1 «Подготовить рекламную кампанию», SP2 «Разработать рекламную кампанию», SP3 «Запустить и сопровождать рекламную кампанию», SP4 «Оценить результаты рекламной кампании».

1. Start «Возникла потребность в проведении рекламной кампании» → SP1 → XOR G1 «Результат подготовки?».
2. G1: «Отказ оформлен» → End «Оформлено решение об отказе»; «Бриф сформирован» → XOR-объединение M2 → SP2.
3. SP2 → SP3 → XOR G3 «Результат сопровождения?».
4. G3: «Период завершён; данные мониторинга подготовлены» → SP4; «Требуется повторное согласование» → M2 перед SP2.
5. SP4 → End «Итоговый отчёт сформирован и передан».

Отказ и запрос повторного согласования записываются результатами подпроцессов. Простое End внутри SP1/SP3 завершает их текущую активацию; родительский маршрут продолжает работу и проверяет результат. После повторного согласования SP3 получает исправленные версии и историю уже выполненных действий. Это та же кампания.

Если смежные пулы показаны на верхнем уровне, провести те же обмены в укрупнённом виде: коммерческие данные к SP1, продажи к SP4, отчёт из SP4, инструкции/материалы из SP3 и ответы магазинов к SP3. На детализациях раскрыть эти обмены, а не придумывать новые.

## Диаграмма 2 — подготовка, A1

Дорожки — директор департамента маркетинга и рекламы и менеджер рекламной кампании. Смежный пул — коммерческий блок. Digital-специалист и trade-маркетолог являются внутренними поставщиками требований каналов; их участие в A13 указать в описании задачи и происхождении данных.

| ID | Обычная задача | Исполнитель | Функция |
|---|---|---|---|
| T11 | Определить потребность в рекламной кампании | Директор департамента маркетинга и рекламы | A11 |
| T12 | Сформировать задачу на проведение рекламной кампании | Директор департамента маркетинга и рекламы | A12 |
| T13 | Собрать исходные данные | Менеджер рекламной кампании | A13 |
| T14 | Сформировать бриф рекламной кампании | Менеджер рекламной кампании | A14 |

1. Start → T11 → XOR G11 «Проводить кампанию?».
2. «Нет» → End «Оформлено решение об отказе». Создание решения входит в T11; шлюз его не создаёт.
3. «Да» → T12 → XOR-объединение M13 → T13 → XOR G13 «Данные полны и проверены?».
4. «Нет» → M13 перед T13; «Да» → T14 → End «Бриф рекламной кампании сформирован».

T13 включает запрос, получение, проверку и ручное объединение данных. Message Flow: T13 → коммерческий пул «Запрос исходных коммерческих данных»; коммерческий пул → T13 «Исходные коммерческие данные». При повторе запрашиваются только недостающие или исправленные сведения. Ожидание ответа входит в укрупнённую задачу; отдельный Receive Task здесь не добавляется.

Data Association: T11 → решение; T12 → задача; задача → T13/T14; коммерческие данные → T13; T13 → сводные исходные данные; сводные данные → T14; T14 → бриф. Стратегия, план продвижения, лимит и условия — ранее заданные основания. T12/T14 используют Word; T13 — Excel; передача выполняется через почтовый клиент и корпоративную почту.

## Диаграмма 3 — разработка, A2

Дорожки — менеджер рекламной кампании, специалист по разработке рекламных материалов, директор департамента маркетинга и рекламы. Смежные пулы не требуются.

| ID | Обычная задача | Исполнитель | Функция |
|---|---|---|---|
| T21 | Разработать концепцию рекламной кампании | Менеджер рекламной кампании | A21 |
| T22 | Сформировать медиаплан | Менеджер рекламной кампании | A22 |
| T23 | Разработать рекламные материалы | Специалист по разработке рекламных материалов | A23 |
| T24send | Передать версии медиаплана и материалов на согласование | Менеджер рекламной кампании | Передача внутри A24 |
| T24 | Согласовать рекламную кампанию | Директор департамента маркетинга и рекламы | Проверка и решение внутри A24 |

1. Start → XOR G20 «Первичная разработка?».
2. «Да» → T21 → XOR-объединение M22; «Нет, повторное согласование» → M22. Концепция уже существует и читается из сохранённых документов.
3. M22 → T22 → XOR G22 «Нужно подготовить или доработать материалы?».
4. «Да» → XOR-объединение M23 → T23 → XOR-объединение M24; «Нет, актуальные материалы уже есть» → M24.
5. M24 → T24send → T24 → XOR G24 «Согласовано?».
6. «Да» → End «Медиаплан и рекламные материалы согласованы».
7. «Нет» → XOR G25 «Что доработать?»: «Медиаплан» → M22; «Материалы» → M23; «Медиаплан и материалы» → M22, затем G22 «Да».

При первом входе материалы обязательно создаются: ветвь G22 «Нет» разрешена только при наличии актуальной версии. При повторном входе T22 проверяет и меняет текущий план по необходимости. Условия G25 взаимоисключающие: это три варианта состава замечаний. Все пути доработки вновь проходят T24send и T24.

Документы: бриф и сводные данные → T21; T21 → концепция → T22/T23; T22 → медиаплан → T23/T24send/T24; T23 → материалы → T24send/T24; T24 → решение, согласованный медиаплан, согласованные материалы или замечания. Замечания → повторные T22/T23. При повторном согласовании данные мониторинга поступают из SP3. Концепция и тексты создаются в Word, медиаплан — в Excel, макеты — в графическом редакторе.

T24send — обычная Task, несмотря на слово «передать»: это ручная отправка внутри одного пула. Между менеджером и директором использовать Sequence Flow и объекты документов. Message Flow между их дорожками не рисовать.

## Диаграмма 4 — запуск и сопровождение, A3

Дорожки — специалист digital-коммуникаций, trade-маркетолог, менеджер рекламной кампании. Смежный пул — магазины. Состав задач сохраняется, но подготовка отделяется от запуска общей проверкой готовности.

| ID | Обычная задача | Исполнитель | Функция |
|---|---|---|---|
| T31d | Подготовить цифровые размещения и email-рассылки | Специалист digital-коммуникаций | Цифровая часть A31 |
| T31r | Подготовить розничное размещение | Trade-маркетолог | Розничная часть A31 |
| T32d | Запустить цифровые размещения и email-рассылки | Специалист digital-коммуникаций | Цифровая часть A32 |
| T32r | Координировать запуск в магазинах | Trade-маркетолог | Розничная часть A32 |
| T33dataD | Собрать данные цифровых каналов | Специалист digital-коммуникаций | Получение показателей внутри A33 |
| T33dataR | Собрать данные розничных размещений | Trade-маркетолог | Получение ответов внутри A33 |
| T33 | Осуществить мониторинг рекламной кампании | Менеджер рекламной кампании | Проверка и координация A33 |
| T33d | Скорректировать цифровое направление | Специалист digital-коммуникаций | Корректировки внутри A33 |
| T33r | Скорректировать розничное направление | Trade-маркетолог | Корректировки внутри A33 |

### Подготовка до общего запуска

1. Start «Медиаплан и рекламные материалы согласованы» → AND-разделение P31.
2. Цифровая ветвь P31 → T31d → AND-объединение J31.
3. Розничная ветвь P31 → XOR-объединение M31r → T31r → XOR G31r «Готовность магазинов подтверждена?».
4. G31r «Нет» → M31r; «Да» → J31.
5. J31 → промежуточный таймер «Дата запуска из согласованного медиаплана» → AND-разделение P32.
6. Цифровая ветвь P32 → T32d → AND-объединение J32.
7. Розничная ветвь P32 → XOR-объединение M32r → T32r → XOR G32r «Размещение подтверждено?».
8. G32r «Нет» → M32r; «Да» → J32.
9. J32 → XOR-объединение M33 → сбор данных для мониторинга.

J31 ждёт готовности обоих направлений, J32 — выполнения обоих направлений запуска. Раньше цифровой запуск мог предшествовать подтверждению общей готовности; этот маршрут исправлен. Таймер содержит дату/время из медиаплана, а не оценку длительности задачи. Если срок уже наступил, календарное ожидание не добавляется. Автоматическая отправка напоминаний не моделируется.

T31d читает контактную базу и создаёт три разных объекта: «Список адресатов рассылки», «Подготовленные email-сообщения», «Параметры цифровых размещений». Они поступают в T32d. Согласованные материалы доступны обеим задачам из SP2. T31r создаёт инструкции, передаёт комплект магазину и собирает готовность. Перед J31 два направления обеспечивают объект «Подтверждения готовности каналов». T32d/T32r создают подтверждения запуска; T32d обновляет журнал рассылок.

### Обмен с магазинами

| Откуда | Куда | Message Flow |
|---|---|---|
| T31r | Пул магазинов | Инструкции и согласованные рекламные материалы |
| Пул магазинов | T31r | Подтверждения готовности магазинов либо замечания |
| T32r | Пул магазинов | Запрос или уточнение статуса запуска |
| Пул магазинов | T32r | Подтверждения размещения |
| T33dataR | Пул магазинов | Запрос данных розничных размещений |
| Пул магазинов | T33dataR | Данные розничных размещений и замечания |
| T33r | Пул магазинов | Уточнённые инструкции в пределах согласованного плана |
| Пул магазинов | T33r | Ответ о выполнении корректировки |

Инструкции и материалы можно передать одним сообщением с двумя вложениями; сами документы показываются отдельными Data Object. Передача документов является допустимым содержанием межпулового сообщения. Ответ магазинов поступает trade-маркетологу, а затем он передаёт сводные данные менеджеру внутри основного пула.

T31r/T32r включают отправку, получение и сверку ответов. Повторная проверка подтверждения не означает повторное физическое размещение; оно выполняется за границей модели. Несколько магазинов представлены одной типовой ролью; сбор их ответов включён в задачу. Multi-instance не добавляется без явного раскрытия работы отдельно по каждому магазину.

### Мониторинг и корректировки

1. M33 → AND-разделение P33data: T33dataD и T33dataR → AND-объединение J33data → T33.
2. T33 → XOR G33a «Период кампании завершён?».
3. G33a «Да» → End «Период кампании завершён; данные мониторинга подготовлены».
4. G33a «Нет» → XOR G33b «Нужно изменить согласованные условия?».
5. G33b «Да» → End «Требуется повторное согласование». Родительский G3 возвращает кампанию в SP2.
6. G33b «Нет» → XOR G33c «Нужны корректировки в пределах плана?».
7. G33c «Нет» → таймер «Следующая дата контроля из медиаплана» → M33.
8. G33c «Да» → OR-разделение P33: «Нужна цифровая корректировка» → T33d и/или «Нужна розничная корректировка» → T33r → OR-объединение J33 → M33.

В P33 выбирается минимум одна ветвь, а J33 ждёт только активированные направления. Заменять J33 на AND нельзя. XOR-объединение M33 пропускает один текущий вход без ожидания: первоначальный запуск, очередную проверку или завершённую корректировку.

T33dataD и T33dataR собирают доступные сведения на текущую контрольную дату; отсутствие ответа фиксируется как пробел, а не скрытое бесконечное ожидание идеального набора. После J33data менеджер получает оба подготовленных набора и вручную сопоставляет их в Excel. Недостающие ответы уточняются в составе сбора данных и мониторинга. Последняя дата графика контроля совпадает с завершением периода; дополнительные контрольные операции поверх сценария расчёта затрат не вводятся.

Данные цифровых каналов и розничных размещений — выходы задач сбора и входы T33. «Данные мониторинга» создаёт T33; они передаются в SP4 либо в SP2 при изменении условий. Корректировки в пределах плана используют зафиксированные отклонения и возвращают работу к проверке результата.

При повторном входе после согласования T31d/T31r актуализируют только затронутые параметры и инструкции, а T32d/T32r применяют согласованные изменения. Уже выполненные действия проверяются по журналу рассылок, ответам магазинов и сохранённым версиям. Рассылка всей аудитории заново и повторное размещение неизменённых материалов не выполняются. Режим повторного входа и актуальная дата применения изменений указываются в описаниях этих задач. После окончания периода новые размещения этой кампании не запускаются; отклонения включаются в отчёт.

## Диаграмма 5 — оценка, A4

Дорожки — маркетинговый аналитик и менеджер рекламной кампании. Смежный пул — коммерческий блок.

| ID | Обычная задача | Исполнитель | Функция |
|---|---|---|---|
| T41 | Собрать результаты рекламной кампании | Маркетинговый аналитик | A41 |
| T42 | Проанализировать эффективность рекламной кампании | Маркетинговый аналитик | A42 |
| T43 | Сформировать итоговый отчёт | Менеджер рекламной кампании | A43, включая передачу |

1. Start → XOR-объединение M41 → T41 → XOR G41 «Данные полны и сопоставимы?».
2. «Нет» → M41 перед T41; «Да» → T42 → T43 → End «Итоговый отчёт сформирован и передан».

T41 читает данные мониторинга из SP3, вновь собирает исходные цифровые и розничные показатели у ранее описанных внутренних исполнителей, запрашивает продажи у категорийного менеджера. Это повторная ручная консолидация, а не автоматический импорт. Message Flow T41 → коммерческий пул «Запрос данных о продажах или уточнений»; обратно → T41 «Данные о продажах».

T41 → «Сводные результаты кампании» → T42/T43. T42 → «Аналитика эффективности рекламной кампании» → T43. Бриф из SP1, медиаплан из SP2, лимит и методика — основания оценки. Аналитик сверяет результаты в Excel, используя данные веб-аналитики и рекламного кабинета. T43 формирует отчёт в Word, сохраняет его и передаёт по почте.

Message Flow T43 → коммерческий пул «Итоговый отчёт». Директор маркетинга получает отчёт внутри основного участника; его адресат указан в описании T43 и объекта отчёта. Отдельная задача чтения отчёта находится за выбранной границей. End означает завершённую передачу обоим адресатам.

## Сверка перед сохранением

1. Каждый обычный шаг маршрута имеет входящий и исходящий Sequence Flow; Start — только исходящий, End — только входящий. Ни одна стрелка не начинается внутри листа в пустом месте.
2. Sequence Flow соединяет элементы одного уровня; Message Flow соединяет разные пулы; чтение и запись файлов показаны Data Association.
3. После проверки стоит подходящий шлюз: XOR для альтернатив, AND для обязательных двух направлений, OR для одного или обоих видов корректировки.
4. Объединение AND не ждёт ветвь, которую могла не запустить предшествующая логика. Все возвраты проходят через обозначенные точки объединения.
5. Бриф, материалы, замечания, мониторинг и отчёт имеют задачи-источники. Постоянные файлы и переписка имеют хранилища; основания кампании заданы в родительском контексте.
6. Все названия ролей согласованы с п. 1.1–1.2; задачи детализации сопоставлены с A11–A43. Внутренние поставщики данных названы в описаниях.
7. На запуске сначала завершается подготовка обоих каналов; повторное согласование сохраняет историю кампании и не запускает повторную рассылку всей базы.
8. Отказ заканчивает процесс, положительный сценарий доходит до передачи отчёта; исправление документов и ожидание ответов образуют понятные возвраты.
9. Ручная работа не заменена значками автоматизации. Цвета, группы и пояснения помогают чтению, но не меняют смысл элементов.

Инструкция определяет исправляемую модель. Ранее сохранённые .bpmn и рисунки этим изменением не обновлены; при их перестроении нужно применить указанные маршруты и обозначения данных.
